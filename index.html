01 / FUNDAMENTOS · DEFINICIÓN

Serverless no significa «sin servidores».

La plataforma gestiona
+Infraestructura física y SO subyacente
+Aprovisionamiento y escalado del runtime
+Recuperación del entorno de ejecución ante fallas
El equipo sigue decidiendo
→Código, datos y permisos
→Resiliencia, calidad y observabilidad
→Costos, cuotas y dependencia del proveedor
Definición: modelo de desarrollo y ejecución en el que el equipo despliega código o utiliza servicios sin aprovisionar ni administrar directamente los servidores subyacentes.

01 / FUNDAMENTOS · MODALIDADES

Tres modalidades comunes. Distintas cosas para delegar.

01

FaaS

Lógica propia en funciones activadas por eventos. Útil para tareas independientes y demanda irregular.

Desplegás: una función
02

BaaS / servicios serverless

Capacidades estándar consumidas por API. Acelera la entrega, con menos control y mayor dependencia.

Consumís: una capacidad
03

Contenedores serverless

Aplicaciones en contenedores sin administrar hosts. Conservan más control sobre frameworks y runtime.

Desplegás: una aplicación
No son opciones excluyentes: una misma aplicación puede combinar las tres.

01 / FUNDAMENTOS · PORTABILIDAD

Vendor lock-in: el costo de abstraer.

ACOPLAMIENTO ALTO
Lógica de negocio mezclada con SDK y runtime
↓
Triggers, empaquetado y configuración específicos
↓
Datos e integraciones dependientes del proveedor
Migrar: reescribir lógica e integraciones; mover datos y probar otra vez.
ACOPLAMIENTO CONTROLADO
Núcleo de negocio independiente
↓
Adaptador de eventos
Adaptador de persistencia
↓
Configuración y despliegue por plataforma
Migrar: reemplazar adaptadores y configuración; igual requiere pruebas.
Mitigar ≠ eliminar: separar dependencias directas y del runtime; usar interfaces y formatos abiertos como CloudEvents cuando correspondan.
Base: artículo de invitado publicado por CNCF (2018) · Portabilidad de empaquetado y eventos · CloudEvents

01 / FUNDAMENTOS · DECISIÓN

Comparar alternativas antes de elegir.

A /

Máquina virtual

El equipo administra el sistema operativo y la capacidad.

  • Conviene: cargas largas o requisitos especiales
  • Control: sistema operativo y runtime
  • Trade-off: mayor operación y planificación
B /

Contenedor administrado

La plataforma gestiona hosts; el equipo despliega la aplicación.

  • Conviene: servicios completos o continuos
  • Control: empaquetado y runtime
  • Trade-off: costos y límites según plataforma
C /

Funciones bajo demanda

La plataforma activa funciones y administra la capacidad.

  • Conviene: tareas independientes y demanda irregular
  • Control: lógica y configuración
  • Trade-off: límites de runtime, duración y latencia
Decisión de negocio: elegir la alternativa que cumple los objetivos de servicio con un costo total y un riesgo aceptables.

01 / FUNDAMENTOS · UNIDAD DE EJECUCIÓN

¿Qué tipo de cómputo conviene?

01 / FAAS

Función bajo demanda

Webhook, validación o tarea breve asociada a un evento.

PRIORIZA
Simplicidad por invocación y elasticidad. Acepta límites de ejecución y posible latencia inicial.
02 / SERVICIO

Contenedor serverless

API o microservicio con dependencias, runtime y ciclo de vida propios.

PRIORIZA
Empaquetado y control de aplicación. Revisar mínimos de capacidad, concurrencia y costo en reposo.
03 / JOB

Procesamiento por lotes

ETL, reporte o conversión de archivos de mayor duración.

PRIORIZA
Ejecución hasta completar una tarea. Evaluar paralelismo, reintentos, duración y costo.
Decisión de negocio: elegir según duración, patrón de tráfico, latencia objetivo, control del runtime y costo total.

02 / ECOSISTEMA · VENDORS

Un modelo. Distintos proveedores.

PUBLIC CLOUD / FaaS

AWS Lambda

Eventos de servicios cloud, APIs y ecosistema amplio. Ejecuciones y cuotas según configuración.

ENTERPRISE INTEGRATION / FaaS

Azure Functions

Triggers, bindings e integración con servicios de Azure. Planes de hosting distintos.

CLOUD + CONTAINERS / FaaS

Google Cloud Run functions

Funciones HTTP o eventos mediante Cloud Run / Eventarc y CloudEvents.

EDGE RUNTIME

Cloudflare Workers

JavaScript/TypeScript y Web APIs cerca del usuario, con modelo de ejecución diferente.

También hay cómputo serverless no-FaaS: contenedores, servicios y jobs. Elegir según integración, región, costos, límites y dependencia.

03 / IMPLEMENTACIÓN · CRITERIOS

Por qué esta arquitectura para la demo.

OBJETIVO DIDÁCTICO

Una demo ejecutable sin salir de las slides.

Cuatro operaciones HTTP muestran ejecución bajo demanda, estado externo, idempotencia y observabilidad.

La presentación no necesita credenciales AWS en el navegador.

Decisión técnica

API Gateway → Lambda → DynamoDB, con logs en CloudWatch.

Compromiso aceptado

API pública de corta duración, datos ficticios y límites de tráfico.

Alcance real

Probamos el mecanismo; no prometemos elasticidad ilimitada ni ahorro sin medirlo.
